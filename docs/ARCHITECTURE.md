# Architecture

DiffRadius investigates the *behavioral impact radius* of a code change instead of treating the diff as
the whole system.

## Production candidate

```text
Ticket + diff + repository
        |
        v
  Impact Scout
  changed contracts -> dependants -> risk hypotheses
        |
        v
Adversarial Reviewer
  counterexamples -> missed paths -> refined hypotheses
        |
        v
 Evidence Verifier
  independently re-opens evidence -> reject/accept
        |
        v
 Release-risk report (Markdown + JSON)
```

All agents receive only five bounded read-only tools: file listing, bounded file reads, text search,
ticket access and diff access. The evaluator's oracle/ground truth lives outside the repository exposed
to agents.

## Why not just one agent?

That is the experiment. A one-agent baseline uses the same model and same repository tools but only a
normal senior-review instruction. The final workflow changes the *reasoning process* by externalizing
three roles: breadth-first impact discovery, adversarial counterexample generation, and independent
claim verification.

The repository runs an ablation matrix:

1. `baseline`: one normal reviewer.
2. `impact`: Scout -> ordinary Synthesizer.
3. `adversarial`: Scout -> Adversary -> ordinary Synthesizer.
4. `final`: Scout -> Adversary -> independent Evidence Verifier.

`adversarial` and `final` intentionally have the same number of model stages. Their difference isolates
verification better than comparing a two-stage workflow with a three-stage workflow.

## Why the verifier re-opens files

Passing an upstream summary directly into a final writer creates correlated failure: a plausible but
wrong statement can survive because every later stage sees the same abstraction. The verifier gets the
candidate list but is instructed to re-open repository evidence. A final finding must be tied to a real
file path and concrete failure mode caused by the diff.

## Evaluation boundary

Evaluation data is split into two worlds:

```text
Agent-visible case                  Evaluator-only data
------------------                  -------------------
ticket                              expected risk categories/paths
after-change repository             oracle test
diff                                before-change repository
read-only tools                     deterministic scorer
```

The source benchmark is public so judges can reproduce it, but each evaluation materializes only the
agent-visible side into the review repository. The oracle is written outside that repository root.

## Trajectory model

Each agent run records:

- its explicit input;
- repository tool calls and bounded outputs;
- its structured output;
- request/token/time/cost usage.

A workflow-level event records the final report and aggregate usage. `diffradius trajectory` renders the
JSON trace as judge-friendly Markdown. These traces deliberately do not expose private model
chain-of-thought.

## Web demo boundary

The Vercel site is presentation, not a second evaluator. It is built from static files and, when frozen
evidence exists, reads the exact `evidence/results/comparison.json` generated by the CLI. This prevents
web polish from becoming a separate source of truth or a place where numbers can drift.

## Safety boundary

- Repository tools are read-only.
- Paths are resolved and checked against the repository root.
- DiffRadius does **not** execute arbitrary target-repository code during an agent review.
- Hosted Agents SDK tracing is disabled by default.
- Local trajectories may contain source snippets, so they should only be generated for code that may be shared.
- No credentials are written to results.
- Benchmark evaluation uses synthetic repositories only.
